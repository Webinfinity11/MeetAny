## B. სპეციფიკაცია — MeetAny

საერთო წესები ორივესთვის: **სამი დონე** — VIP → ტოპ → ჩვეულებრივი. სიის შუაში მართვის ელემენტი (toggle/„მეტის ჩვენება“) არასდროს — ერთი უწყვეტი სია, ჩვეულებრივი ჩანაწერები პირდაპირ გრძელდება VIP/ტოპის შემდეგ. მთავრული მხოლოდ სათაურებსა და ღილაკებზე (ბეიჯის ტექსტი მთავრულში, რადგან ის UI-ლეიბლია, არა თავისუფალი ტექსტი — `--ff-heading`/`--theme-caps-*` ტოკენებით). ცარიელი placeholder არასდროს. ფერი/ჩარჩო მხოლოდ ახალი ტოკენებით.

### B0. ახალი ტოკენები (წინადადება, `tokens.css`-ში დასამატებელი)

არსებული პალიტრიდან ვღებულობ — ახალი ფერი არ შემოაქვს, მხოლოდ არსებული `--orange-*` (accent, უკვე „ბეიჯი/აქცენტი“ როლშია) და `--blue-*` (brand) გადანაწილება ტირის მიზნით:

```
--tier-vip-bg:var(--orange-50);        /* VIP ბარათის ფონი — თბილი, არა ალარმისებური */
--tier-vip-border:var(--orange-300);   /* VIP ბარათის ჩარჩო */
--tier-vip-text:var(--orange-700);     /* VIP ბეიჯის ტექსტი/აქცენტი */
--tier-vip-badge-bg:var(--orange-400); /* VIP ბეიჯის ფონი (მყარი ფერი, არა ტონალური) */
--tier-top-bg:var(--blue-50);          /* ტოპის ფონი — ბრენდის ლურჯი, მშვიდი */
--tier-top-border:var(--blue-200);
--tier-top-text:var(--blue-700);
--tier-top-badge-bg:var(--blue-100);
```
რატომ ორანჟი VIP-ისთვის და ლურჯი ტოპისთვის: `--theme-accent` უკვე „ბეიჯი/გამორჩევა“ როლშია (`--orange-400` „accent FILL only“), ლურჯი კი ბრენდის/ქმედების ფერია — ასე VIP ერთადერთი ადგილი რჩება, სადაც accent ფერი დომინანტურია, ტოპი კი ჩვეულებრივ ბრენდულ ენაშივეა, უბრალოდ თამამი ფონით. საფრთხე: ორანჟი ფონი `--warning-50/100`-ს ჰგავს — ბეიჯს აშკარა ტექსტი სჭირდება („VIP“), ფერი მარტო არ კმარა (Baymard/NNg-ს ხელმისაწვდომობის პრინციპი, ფერი მარტო არ ატარებს მნიშვნელობას).

### B1. მოთხოვნები — ცოცხალი დაფა

**სტრუქტურა:** გვერდის თავში, ჩვეულებრივი ფილტრების/ResultsBar-ის ქვემოთ, **VIP+ტოპ ზონა** — მხოლოდ თუ არსებობს მინიმუმ ერთი ასეთი ჩანაწერი (თორემ ზონა საერთოდ არ იბეჭდება, ცარიელი კონტეინერი არასდროს). ზონის შემდეგ პირდაპირ გრძელდება ახლანდელი კომპაქტური სია (6963c4f ბარათი, უცვლელი) ყველა დანარჩენი ჩანაწერით, ვადის/„ახალი“-ს ჩათვლით.

**ვარიანტი A — დიდი ბარათები, ერთ სვეტად** (1440px-ზე 2 სვეტი grid, 390px-ზე 1 სვეტი):
- VIP ბარათი: `.ma-rcard` საბაზო სტრუქტურაზე, მაგრამ `--card-pad` × 1.25, ფონი `--tier-vip-bg`, ჩარჩო 1.5px `--tier-vip-border`, ზედა მარცხენა კუთხეში ბეიჯი „VIP“ (`--tier-vip-badge-bg` ფონი, თეთრი ტექსტი, mtavruli). ფოტო დიდი (თუ ავტორს აქვს), სათაური `--fs-title`-ზე ერთი საფეხურით დიდი (`--fs-h3`), ვადის ათვლა თვალსაჩინო ადგილას (მაგ. „2 დღე დარჩა“ წითელი/warning ტექსტით ვადის სიახლოვისას — არსებული `--warning-600`), „ახალი“ ნიშანი (`--success-*` ან `--blue-*` badge) თუ 24სთ-ზე ახალია.
- ტოპ ბარათი: იგივე კონტეინერი, `--tier-top-bg`/`--tier-top-border`, ბეიჯი „ტოპ“ (`--tier-top-badge-bg` ფონი, `--tier-top-text`), ზომა შუალედური — `--card-pad` × 1.1, სათაური `--fs-title` (ჩვეულებრივი ზომა, არა გადიდებული).
- 1440px: grid 2 სვეტი, VIP პირველი რიგი (თუ 2+ VIP-ია), ტოპი მეორე რიგიდან; 390px: ერთი სვეტი, ჯერ ყველა VIP მერე ყველა ტოპი.

**ვარიანტი B — ჰორიზონტალური carousel-ტიპის ზოლი** VIP-სთვის (scroll-x მობილურზეც, 1440-ზე ჩანს 3), ტოპისთვის ჩვეულებრივი grid: ამან **სცადა** დაარღვიოს „სიის შუაში მართვის ელემენტი არასდროს“-ის სულისკვეთება (carousel-ის ისრები/scroll UI-ია, ცალკე მართვის ღილაკი არაა, მაგრამ ჰორიზონტალური scroll თავად არის დამატებითი ინტერაქცია) — **არ ვურჩევ** ამის გამო B2B მარტივი UX-ისთვის.

**რეკომენდაცია: ვარიანტი A.** მიზეზი: 1) ss.ge-ს დადასტურებული პატერნი (ბეიჯი+პოზიცია საკმარისია, ზომის დრამატული ცვლილება არა) მიუთითებს, რომ ზომიერი გადიდება (×1.1–1.25) საკმარისია იერარქიისთვის, ჰორიზონტალური scroll კი ახალი ინტერაქციის სირთულეა მარტივი B2B-სთვის; 2) grid ორივე სიგანეზე ბუნებრივად აგრძელებს ქვედა ჩვეულებრივ სიაში კურსორის/სქროლის მიმართულების შეცვლის გარეშე; 3) მობილურზე ვერტიკალური დაწყობა უფრო ხელმისაწვდომია (VoiceOver/TalkBack რიგითობა) ვიდრე scroll-x კონტეინერი.

**მობილურზე (390px) რამდენი ეტევა პირველ ეკრანზე:** header (56px) + ResultsBar (~52px) + 2 VIP ბარათი (თითო ≈180–200px ფოტოთი) ≈ 56+52+2×190 = **≈488px** — iPhone SE (667px) ჩანაწილზეც 2 VIP მთლიანად ჩანს, მე-3-ის თავი უკვე მაჩვენებელია რომ სია გრძელდება (გადაფარვის ეფექტი კარგია, არა ცუდი). **VIP+ტოპ ზონის ჯამური სიმაღლის ჭერი ≈ 1 ეკრანი** (390×667-ზე ≈650px) — ესე იგი მაქს. **2 VIP + 2 ტოპი** მობილურზე ერთდროულად ჩვენება ჩვეულებრივი სიის დაძირვის გარეშე; მეტი რომ იყოს ბაზაში, დარჩენილი ტოპები პირდაპირ ჩვეულებრივ სიაში ჩავარდება ბეიჯის გარეშე (ანუ ტირი მონაცემია, ვიზუალური ზონა კი შეზღუდულია ბოლომდე).

მოთხოვნებზე **ვარიანტი A** (ზომიერად გადიდებული ბარათები VIP/ტოპ ზონაში, grid — არა carousel) და კომპანიებზეც **ვარიანტი A** (თანასწორი grid ფილები „რჩეული მომწოდებლები“ სექციაში, არა ერთი hero row): ორივე ინარჩუნებს „მარტივი, სწრაფი B2B UX“-ს და „სიის შუაში მართვის ელემენტი არასდროს“-ის წესს, ამატებს რა ss.ge-ს დადასტურებულ პატერნს (ბეიჯი+ზომიერი ზომა+პოზიცია, არა რადიკალური ზომის სხვაობა) და Alibaba/Europages/Thomasnet-ის პატერნს (რანჟირება ბეიჯს უნდა შეესაბამებოდეს, თორემ ბეიჯი უფასურდება). ორივე გვერდზე ტირი ვიზუალურად ცალკე ენაზეა აგებული — მოთხოვნებზე დროზე ორიენტირებული (ვადა, „ახალი“), კომპანიებზე იდენტობაზე (ლოგო/ინიციალი) — რაც პირდაპირ პასუხობს მფლობელის პრეტენზიას, რომ ორი გვერდი ერთმანეთს ჰგავს.

## D. კრიტიკა — რისკები

- **„ყველა VIP“ ეფექტი:** თუ ტირის მინიჭება თავისუფალი/იაფია, ყველა მოითხოვს VIP-ს და იერარქია ქრება (Alibaba-ს ისტორია ზუსტად ეს არის — Gold გახდა ჩვეულებრივი, ამიტომაც შემოვიდა Verified). **შემარბილებელი:** ეტაპ 2-ზე რაოდენობრივი ლიმიტი (მაგ. მაქს. 3 VIP ერთდროულად თითო კატეგორიაზე) ან ვადიანობა (`tier_until`), არა უსასრულო წევრობა.
- **გადატვირთვა/ხმაური:** ორი ახალი ფონის ფერი (ორანჟი+ლურჯი) ერთ გვერდზე რისკავს ვიზუალურ ხმაურს კომპაქტურ ჩვეულებრივ სიასთან შედარებით. **შემარბილებელი:** VIP/ტოპ ზონა მკაცრად შემოსაზღვრული (≤1 ეკრანი), ჩვეულებრივი სია ტოტალურად უცვლელი რჩება — კონტრასტი მხოლოდ ზონის შიგნითაა, არა მთელ გვერდზე.
- **მობილური:** 2 სვეტიანი კომპანიის ფილი 390px-ზე ვიწროა ქართული გრძელი კომპანიის სახელებისთვის (მაგ. „ავეჯის სახელოსნო „ხე““) — საჭიროა ტესტი რეალურ ტექსტზე, კოდის წერისას აუცილებელი შემოწმება 2 ხაზზე გადატანით overflow-ის გარეშე.
- **ხელმისაწვდომობა:** ბეიჯის ტექსტი („VIP“/„ტოპ“) სავალდებულოა, არა მხოლოდ ფერი — screen reader-მა ტირი უნდა წაიკითხოს (`aria-label` ან ხილული ტექსტი, არა მხოლოდ ფონის ფერი/ხატულა).
