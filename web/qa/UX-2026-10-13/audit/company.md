ძირითად გაზომვებში `docOverflow=0`. მობილურ პროფილსა და standalone offer ფორმას ქვედა sticky მოქმედება არა აქვს; onboarding-ს 69px ქვედა ზოლი აქვს. `fixedBottom` ალგორითმის ყველა ჩანაწერი sticky footer არ არის: მაგალითად მარჯვენა preview `aside` მხოლოდ თავისი CSS პოზიციისა და კოორდინატების გამო ხვდება სიაში. `clipped`-ის 1×1 დამალული chat label-ები accessibility ტექსტია და პრობლემად არ ჩაითვალა. იგივე ეხება custom select-ის დამალულ 1×1 native კონტროლებს და checkbox-ის input-ს, როცა გარშემო დიდი label-ია. რეალური მცირე სამიზნე CO-20-შია.

მობილური მაღალი გვერდის PNG-ში header ზოგჯერ შუა ნაწილში ჩანს: full-page გადაღება submit-ის მიერ შეცვლილი scroll პოზიციიდან მოხდა; ეს თავისთავად დუბლირებული ჰედერის ბაგის მტკიცებულება არ არის. ორიგინალი სრული PNG-ები და მათი main ტექსტები შენახულია; overview contact-sheet-ებიც შედარებისთვისაა.

**ThreadRig browser:** საკუთარი `company` ტაბით UI-ში შესრულდა შესვლა owner_company-ით, „პარამეტრები“, სახელის გასუფთავება, submit, სახელის აღდგენა, უცვლელი ფორმის save („ცვლილებები შენახულია“ დადასტურდა DOM-ით), აღწერის დროებითი ცვლილება, „პროდუქტები“ და browser Back. ეკრანის ზომა იქ 2591×1619 იყო; მოთხოვნილი ორი ზომის მტკიცებულება Playwright-იდანაა. browser საერთო cookies-სა და screenshot output path-ს სხვა აგენტებთან იზიარებდა: ერთი დაბრუნებული PNG სხვა აქტიურ გვერდს აჩვენებდა. ის `browser-shared-capture-mismatch.png`-ად ცალკე დარჩა და **არცერთი აღმოჩენის მტკიცებულებად არ გამოიყენება**. browser Back-ის ამ გაზიარებულ სესიაში დაბრუნების ზუსტი ისტორია სანდოდ ვერ შეფასდა; draft-ის დაკარგვა იზოლირებულ Playwright-შია დადასტურებული.

## რა ვერ შემოწმდა და რატომ

- ფიზიკური iOS/Android კლავიატურა და მისი submit-თან გადაფარვა: desktop Chrome-ის viewport ტესტი რეალურ ეკრანულ კლავიატურას არ აჩვენებს. გაზომილია ზომა/scroll/sticky, არა keyboard-safe-area-ის სრული ქცევა.
- CLS-ის რიცხვითი Web Vitals გაზომვა არ ჩატარებულა; ჩატვირთვის skeleton/progress არსებობა UI/კოდში შემოწმდა. settle-ის შემდეგ screenshot არ ამტკიცებს CLS=0-ს.
- owner-ის ვერიფიკაციის წარმატებული განხილვა, დაბრუნებული დოკუმენტები და admin approval: საჭირო ნამდვილი იურიდიული ფაილები არ შექმნილა/მოგონილა. ცარიელი submit და არსებული verified/readOnly ხედი შემოწმდა.
- wood-ის საწყის სიაში **complete** ეტაპის გარიგება არ იყო. progress რეალურად მივიღეთ supplier მოქმედებით; დასრულება და შეფასების დაწერა buyer-ის უფლებაა. `DealViewPageContent.tsx`-ში supplier complete ხედს აქვს „მყიდველს ჯერ არ შეუფასებია“ ან არსებული შეფასება, მაგრამ ეს ნაწილი runtime screenshot-ით არ არის დადასტურებული. ამიტომ complete-ისათვის გამოგონილი capture არ არსებობს.
