# P13 T13.1 — ვიზუალური რეგრესია

აპის იერი და დემო-შინაარსი არ იცვლება. ჰარნესი მხოლოდ `qa/visual/`-შია; საერთო dev სერვერს არ იწყებს და არ აჩერებს. Mobbin-ის ახალი რეფერენსები არ დამატებულა, რადგან UI არ იცვლება.

## გაშვება

`site/web`-დან, უკვე გაშვებულ `http://localhost:3001`-ზე:

```sh
npm run visual:baseline
npm run visual:diff
npm run visual:diff -- --only guest-requests
npm run visual:diff -- --update --only guest-requests
node --test qa/visual/lib/*.test.mjs
```

`visual:baseline` იგივეა, რაც `visual:diff -- --update`. `--only` იღებს ზუსტ id-ს `qa/visual/pages.mjs`-დან; არარსებული სახელი შეცდომაა. განახლების გარეშე დაკარგული baseline შეცდომაა, ავტომატურად არ იქმნება. სრული baseline-ის შემდეგ დაუყოვნებლივ გაუშვი სრული diff. ახალი კოდის მიღებისას baseline მხოლოდ განხილვის შემდეგ განაახლე.

საჭიროა დაინსტალირებული Google Chrome (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`), npm dependencies და არსებული demo ledger. საჭიროებისას `QA_BROWSER_PATH` ცვლის Chrome-ის გზას, `QA_ORIGIN` — ლოკალურ მისამართს. ledger იკითხება მხოლოდ სკრიპტიდან, პაროლი არ იბეჭდება; ავტორიზაციის შევსებული ფორმის კადრები არ იქმნება. `.env.local`-ის `DATABASE_URL`-ის ჰოსტი მოწმდება `ep-withered-glade-b54ts1g5` პრეფიქსზე. ჰარნესი DB-ს პირდაპირ არ უკავშირდება.

ერთ გაშვებაზე ერთი Chrome მუშაობს, გვერდები თანმიმდევრულია. ნელი ნავიგაცია და ჩავარდნილი გადაღება ერთხელ მეორდება. გაუშვი სხვა გადაღებებისა და build-ის დასრულების შემდეგ, უცვლელ დემო-მონაცემებზე. ჰარნესი არც მოთხოვნებს, არც შეთავაზებებს, პროფილებსა და შეტყობინებებს არ ქმნის/არ ცვლის. ChatPopup-ის არჩეულ არსებულ საუბარში შეტყობინებები არ არის; ამიტომ კადრი აპის ნამდვილ ცარიელ მდგომარეობას აჩვენებს. კლიენტის ინბოქსში კი არსებული შეტყობინებები ჩანს. API route guard ატარებს მხოლოდ წაკითხვებს, `mark_read`-სა და ავტორიზაციის/სესიის მოთხოვნებს. სხვა ჩაწერა abort-ს და მთლიანი გაშვების FAIL-ს იწვევს. ChatPopup-ის მხოლოდ `start_conversation` RPC ჩანაცვლდება `list_my_conversations`-იდან მიღებული არსებული საუბრის ობიექტით; დანარჩენი RPC-ები რეალურია.

## კადრები და შედარება

24 მდგომარეობა, 47 კადრი: 1440×1000 და 390×844, `fullPage: true`, deviceScaleFactor 1. მთავარი გვერდი მხოლოდ 1440-ზე, ერთი კადრია. მობილური სრული სიმაღლე >4000px შეცდომაა; ჰარნესი არ ჭრის და არ ამცირებს კადრს. Desktop ინბოქსი აპის წესით პირველ საუბარს ავტომატურად ხსნის; ამიტომ სიისა და გახსნილი საუბრის ორი მდგომარეობა desktop-ზე შეიძლება იდენტური იყოს.

`qa/shots/visual-baseline/manifest.json` ინახავს HEAD-ს, Chrome-ის ვერსიას, viewport-ებს, მასკებს, აღმოჩენილ მოთხოვნის/კომპანიის/საუბრის id-ებსა და კადრების ზომებს. შემდეგი გაშვება იმავე id-ებს იყენებს. საბოლოო baseline-ის რევიზიაა `3c69b9c` (P12 T12.5b). baseline-ის განახლებას აპის დაკომიტებული მდგომარეობა სჭირდება. `visual:diff` მუშაობს ადგილობრივ, ჯერ დაუკომიტებელ რეფაქტორზეც: ყოველი კადრის წინ ამოწმებს საწყისი სამუშაო ხის SHA-256 ანაბეჭდსა და უცვლელ HEAD-ს, რათა ერთ გაშვებაში სხვადასხვა ცვლილება არ აირიოს. წარუმატებელი `--update` არ ცვლის მიღებულ PNG-ებს: დროებითი გადაღებები მხოლოდ მთელი არჩეული ნაკრების წარმატების შემდეგ გადადის baseline-ში.

`pixelmatch`-ის ფერის მგრძნობელობის `threshold` არის 0.1, `includeAA: true`; მიღების ცალკე ზღვარია შეცვლილი პიქსელების ≤0.1%. განსხვავებული ზომები ყოველთვის FAIL-ია. კონსოლში გამოდის გვერდი × viewport × % × PASS/FAIL; `qa/shots/visual-diff/report.json` იგივე შედეგებს ინახავს. მიმდინარე diff-კადრები და report-ები Git-ში იგნორირებულია; მიღებული სტაბილურობის ანგარიში baseline-ის `stability.json`-ში ინახება. განსხვავების PNG იქმნება მხოლოდ FAIL-ზე; წარმატებული ხელახალი შემოწმება ამავე კადრის ძველ diff-ს შლის. FAIL ან გადაღების შეცდომა იძლევა არანულოვან exit code-ს. `--only` ცალკე `report-<page>.json`-ს წერს, სრული სტაბილურობის ანგარიშს არ გადაწერს.

## ადმინის სრული მობილური კადრის ზომა

ნაგულისხმევი სრული სიები 4000px-ს სცდება (მოთხოვნები 6555px; ჟურნალის ბოლო გვერდი 8802px). კადრი არ იჭრება, CSS ზომები არ იცვლება და RPC მონაცემები არ იცვლება. ორივე viewport ერთსა და იმავე რეალურ, URL-ით არჩეულ მდგომარეობას იღებს:

- `admin-requests`: ძიება `q=სასტუმრო` — სამი მოთხოვნა.
- `admin-users`: `role=client&q=demo-hotel@meetany.ge` — ერთი დემო კლიენტი.
- `admin-audit`: რეალური გვერდებად დაყოფა; თუ ბოლო გვერდიც მაღალია, არსებული ჩანაწერის `created_at/id` და პასუხის `asOf` ქმნის აპის მხარდაჭერილ cursor URL-ს ბოლო მოკლე მონაკვეთისთვის. მიღებულ კადრში ექვსი ჩანაწერია; საჭიროების შემთხვევაში დარჩენილი რაოდენობა კიდევ მცირდება. მონაცემი არც იწერება, არც ყალბდება.
- `admin-contacts`: `period=day&kind=call`; საჭიროების შემთხვევაში იგივე cursor წესი.

ზუსტი, არჩეული URL-ები `manifest.json`-ში ინახება და მომდევნო diff იმავეს იყენებს. ნაგულისხმევი ადმინის გაუფილტრავი სიის მთლიანი მობილური სიგრძე ამ baseline-ის ფარგლებს გარეთაა. დანარჩენი გვერდები ნაგულისხმევი ან დავალებით მოთხოვნილი მდგომარეობით გადაიღება.

## დეტერმინიზმი და მასკები

`reducedMotion: reduce`, CSS `animation/transition: none`, დამალული caret და Next dev indicator; ქართული locale და Asia/Tbilisi timezone. გადაღება ელოდება ჩატისა და მობილურის portal-ში მოთავსებული საუბრის შეტყობინებებს, `document.fonts.ready`, `networkidle`, ყველა `img.complete`-ს. ბუნებრივ lazy ატვირთვას გვერდის ჩამოსქროლვა ააქტიურებს; `img.loading` და React-ის hydration ატრიბუტები არ იცვლება. ბოლოს გვერდი თავში ბრუნდება.

მასკა ფარავს მხოლოდ შერჩეული ელემენტის ხილულ ნაწილს: დიალოგის უკან მოქცეული ნაწილი გამოირიცხება, რომ ფონის დროის მასკამ ფორმის ველი ან ჩატის სათაური არ დაფაროს. ამისთვის იქმნება გამჭვირვალე, აბსოლუტურად პოზიციონირებული მართკუთხედები; გვერდის განლაგება უცვლელია.

მასკების ერთადერთი სიაა `qa/visual/pages.mjs`; ფერი `#CBD5E1`, ერთფეროვანი მართკუთხედი:

- `time`, მოთხოვნის გამოქვეყნების `.detail-meta__line`, კომპანიის თარიღიანი `.company-profile-activity`, `.request-card-meta`, deadline სტატუსები, მოთხოვნის ვადის/საჭირო თარიღის `dd`, `.inbox-day`: თარიღები და ფარდობითი დრო.
- `.account-row__meta`, `.ma-ocard .ma-meta`, ადმინის მოთხოვნის `small`: თარიღის შემცველი მეტამონაცემების რიგები; ამ რიგების სხვა ტექსტიც გამორიცხულია pixel-diff-იდან.

- `[data-visual-private]`: დამატებითი ტექსტური შემოწმება ნომრის შემცველ ელემენტებზე, მათ შორის საუბრის ტექსტზე. მოწმდება body-ში არსებული ტექსტი, მათ შორის main-ის გარეთ გახსნილი ფანჯრები; თავად მონაცემი არ იცვლება, ფარავს მხოლოდ screenshot-ის mask.

პირველ შედარებაში მოთხოვნების მობილური სია იყო 0.14412%: ფარდობითი დროის სიგანის ცვლილებამ „ახალი“ წარწერა გადაადგილა. იგივე მიზეზი მოთხოვნის მოდალის ფონზეც გამოჩნდა (0.14079%). ამიტომ კატალოგში და მოდალის ხილულ ფონზე `.request-card-meta` მთლიანად იფარება — თარიღთან ერთად კატეგორია, ქალაქი, რაოდენობა და ავტორიც; სათაური, ფოტო და ბარათის საზღვრები მოწმდება.

ეს უბნები დიზაინის რეგრესიისგან დაცული არ არის; მათ ხელით გადახედვა სჭირდება. არსებული შეტყობინებების მონაცემები ხელუხლებელია; კადრში მხოლოდ ნომერი იფარება. ანგარიშში `safety` აჩვენებს დაბლოკილ ჩაწერებსა და `start_conversation` interception-ების რაოდენობას.
